The previous chapter ended with a machine that reads a passage of text and says what is likely to come next. That machine is not ChatGPT. It will not answer your question, stop to think, or look anything up. This chapter covers what gets added on top: the training that turns a text predictor into an assistant, the hidden thinking tokens, the tool calls, and the transcript format that makes the whole thing feel like a conversation.

## What a Raw Model Does

A transformer (<Ch slug="transformers" />) trained to predict the next word (<Ch slug="next-word-prediction" />) is called a *base model*, and that training is called *pre-training*. It reads an enormous amount of text, and what it gets out of it is an understanding of how the world works.

What it does not get is any sense of what to do with that understanding. Predicting the most likely next token is often not what you would want from a helpful assistant. The playground shows a few examples.

</RawCompletionWidget>

The base model is not confused and it is not stupid. It is doing exactly what we trained it to do. What we trained it to do was predict the next token, not be a useful assistant. 

## Post-Training

Closing that gap is a whole second stage of training. The two stages have names:

- **Pre-training** is next-word prediction over a very large body of text. It is where the model picks up its understanding of how the world works. Nearly all of the compute goes here, often more than 99% of it.
- **Post-training** is everything after that. It teaches the model how to apply that understanding to the thing you actually want. It is a thin layer, and it accounts for all of the difference between the two completions in the playground above.

There are several ways to do post training, and a modern chat model has usually been through most of them. Most work the same way underneath: produce several candidate responses, score them somehow, and adjust the weights so that higher-scoring responses become more likely.

</TrainingSignalWidget>

Post-training does not teach the model new facts or new ways of understanding the world. It teaches it how to apply the understanding it already has to do something useful.

## Thinking Before Speaking

Ask a person a hard question and demand an answer in the next half second, and they will do badly. Not because they cannot solve it, but because solving it takes steps and they were not given room for any.

A transformer has the same problem. Each token gets a fixed amount of computation, a fixed number of layers. A question needing ten steps of work does not get ten times the compute just because it is harder.

*Reasoning models* fix this in about the most direct way possible. The model is allowed to write to itself first. It emits tokens into a thinking section that the product does not show you, works through the problem there, and then writes the answer. Nothing about the architecture changes. There is no new component, no extra network. The thinking tokens are predicted exactly like every other token, and the model reads them back the same way it reads anything else in its context. Its own output becomes its working memory.

<ThinkFirstWidget>

</ThinkFirstWidget>

What made this work was the verifiable rewards from the previous section. If you can check the final answer automatically, you can reward whatever scratchpad led to it, without anyone having to specify what good reasoning looks like. Models trained this way picked up habits nobody wrote down: checking their work, backing out of a dead end, noticing halfway through that an earlier step was wrong.

The trace is doing real work. The model reads it back, and the answer changes because of what is in it, which is what the playground above is showing. What it does not come with is a guarantee that it is the whole story. Anthropic ran an experiment where a hint about the answer was slipped into the prompt. Models often took the hint, and then wrote a confident chain of reasoning that never mentioned it and arrived at the hinted answer by a route assembled afterwards. People do this all the time. The reasons someone gives for a conclusion are not always the reasons that produced it. So the trace is worth reading and worth trusting more than nothing, and it is not an audit trail.

More thinking is also not always better. Every thinking token costs time and money, and on an easy question a long trace mostly gives the model more chances to talk itself out of the right answer.

## Tools

A model can only do one thing: write text. So tool use has to be made of text, and it is.

The list of available tools goes into the model's context as a description of each one and what it is for. When the model wants to use a tool, it writes a tool call, a short structured piece of text naming the tool and its arguments. The program running the model, sometimes called the harness, watches for that. When it sees one, it stops generation, actually runs the search or the calculator or the code, and pastes the result back into the transcript as a new turn, in the same way a user's message would arrive. Then the model carries on from there.

That loop repeats until the model writes an ordinary reply instead of another tool call.

This is all "the model searched the web" means. It is also worth being clear that the model does not run anything. It writes a request, something else acts, and the model finds out what happened by reading. Grounding an answer in a real search result makes it much more likely to be right, though the model is still the one writing the summary, so it is still capable of getting it wrong. <Ch slug="hallucination" /> takes that up.

## Skills

The tool list from the last section is itself just text sitting in the context: a name and a short description for each tool the model is allowed to use. That is the only way the model knows any of them exist.

*Skills* run on the same mechanism, because a skill is a tool whose result is a page of instructions. The model is given a list of skill names, one line each on when the skill applies. When one looks relevant it writes a tool call asking for that skill, and what comes back is not a search result or a forecast. It is the instructions: how to do this particular task, step by step. The tool's whole job is to hand over some standard text.

Those instructions then sit in the context and the model works from them. A person with a folder of checklists does the same thing. You do not memorise the pre-flight checklist, you know one exists and you fetch it when you need it.

The two-step exists because loading every skill's full instructions into every conversation would be enormous and almost all of it would be irrelevant. One line each is cheap. The document only arrives when it is about to be used.

It also has to work this way, because nothing the model learns during a conversation survives it. The weights do not change while you talk to it. Any capability added after training arrives as text placed in the context, which is the same reason telling a model something useful in one conversation does nothing for the next one.

## Making It a Conversation

Underneath every chat interface there is a single stream of tokens. The model does not see turns. It sees one document with markers in it saying who is speaking, something along the lines of:

```
<|system|>You are a helpful assistant. Today is 27 August 2026.
<|user|>What's the capital of Australia?
<|assistant|>Canberra.<|end|>
<|user|>Are you sure?
<|assistant|>
```

The format is called a *chat template*, and the markers are real tokens the tokeniser knows about. Post-training is what taught the model to continue after the assistant marker, to answer rather than to carry on inventing user messages, and to emit the end marker when it is done so the harness knows to stop.

The system prompt is nothing more special than text at the top of that document. That is why it works, and also why it is not a hard guarantee. Everything the model knows about the conversation is in the transcript in front of it, which is why the size of that transcript matters so much. <Ch slug="context" /> is about managing it.

## Putting It Together

A chat model is a next-token predictor with four things layered on top. Post-training aims it at being helpful rather than at continuing a document. Thinking tokens give it room to work before it commits to an answer. Tool calls let it act on the world by writing text that something else executes. And a chat template arranges the whole exchange as one document for it to continue.

None of that changes the machine from the last chapter. The transformer is doing the same thing it was doing at the end of <Ch slug="transformers" />, predicting one token at a time. Everything in this chapter is about what it gets asked to predict, and what happens to the text once it has.
