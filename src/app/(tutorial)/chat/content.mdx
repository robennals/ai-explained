The previous chapter ended with a machine that reads a passage of text and says what is likely to come next. That machine is not ChatGPT or Claude. This chapter is about the training that turns a next word predictor into something useful.

## What a Raw Model Does

A transformer (<Ch slug="transformers" />) trained to predict the next word (<Ch slug="next-word-prediction" />) is called a *base model*. This model has read an enormous amount of text and has formed a deep enough understanding of how the world works that it can predict the next work in a piece of text about pretty much anything.

But predicting the next word is not what you usually want a helpful assistant to do. The playground shows a few examples.

Try each <nog>prompt</nog>. The completion is not a mistake. Ask yourself where on the internet that text would have come next.
</RawCompletionWidget>

The base model is not confused and it is not stupid. It is doing exactly what we trained it to do. What we trained it to do was predict the next token, not to be a useful assistant.

## Post-Training

Closing that gap is a whole second stage of training. The two stages have names:

- **Pre-training** is next-word prediction over a very large body of text. It is where the model picks up its understanding of how the world works. Nearly all of the compute goes here, often more than 99% of it.
- **Post-training** is everything after that. It teaches the model how to apply that understanding to the thing you actually want the model to do. It is a thin layer, and it accounts for the difference between the completions above and the assistant you are used to.

It is worth being clear about what post-training is not. The model has already read a great deal of real back-and-forth conversation, and a great many genuinely helpful answers. It can already produce the kind of response you want. That response is simply not the most likely thing it will say, and not what it will pick when left to itself. Post-training does not teach the model a new kind of completion. It steers it towards the completions we want and away from the ones we do not.

There are several ways to do that, and a modern chat model has usually been through most of them. Most work the same way underneath: produce several candidate responses, score them somehow, and adjust the model's weights so that higher-scoring responses become more likely.

</TrainingSignalWidget>

Post-training does not teach the model new facts or new ways of understanding the world. It steers it towards using what it already has in the way we want.

## Making It a Conversation

Underneath every chat interface there is a single stream of tokens. The model does not see a conversation. It sees a prompt and writes a completion, exactly as in the first playground of this chapter. Post-training is what changed the completion from whatever text would plausibly have come next into an answer. What makes it a conversation is markers in the prompt saying who is speaking.

<TranscriptViewsWidget>
The same exchange twice. As text, it is a prompt and a completion. As messages, it is what you would see on screen, plus one the human is never shown.
</TranscriptViewsWidget>

The format is called a *chat template*. Every turn is opened and closed, and the markers are real tokens the tokeniser knows about. The program running the model writes the system and human turns, and the marker that opens the model's turn. The model writes its reply, and then the marker that closes it, which is how the program knows the reply has finished. The exact markers vary from model to model, though the shape does not.

The system prompt is nothing more special than text at the top of that prompt. That is why it works, and also why it is not a hard guarantee.

## Repeated Turns

A real conversation is several turns. The way we handle that is simple. Each time you send a message, we pass the model every message so far, including the ones it wrote itself, and ask it to complete the text by saying what comes next.

<RepeatedTurnsWidget>
Step through the three replies and watch the prompt grow. Everything the model said earlier is in there too, sent again. Switch to **As messages** to see the same thing as the conversation you would see on screen.
</RepeatedTurnsWidget>

The model is run fresh every time. Its only knowledge of its past self is the messages we tell it it wrote.

It might seem wasteful to make the model re-read the whole conversation before every reply. As <Ch slug="context" /> shows, it can be made efficient by caching the attention vectors for prefixes the model has already seen, so the re-reading is mostly free.

## The System Prompt

There is one more message in a real conversation, and you never see it. Before your first message, the program puts a *system prompt* at the top: text telling the model things it could not have learned during training. What it is called and how it should behave. Today's date. Where you are.

<SystemPromptViewWidget>
Switch between the two views. It is the same stream of tokens as before, with one more message at the front, and that message is the one you are not shown.
</SystemPromptViewWidget>

From here on, this tutorial draws conversations as messages rather than as raw tokens, because they are easier to follow. A message drawn with a dashed outline, like the system prompt above, is one the human is never shown. <Ch slug="agents" /> uses that for a lot more than the system prompt: it is where the model is told about the tools and skills it can use.

## Putting It Together

Turning a next-token predictor into a chat model takes two things. First we use post-training to steer it towards the kind of completion that reads like a helpful reply, rather than whatever else it might have said. Then we wrap it in a harness that arranges the exchange as one document, hands the whole thing over each turn, and presents what comes back as a conversation.

The transformer is doing the same thing it was doing at the end of <Ch slug="transformers" />, predicting one token at a time. What changed is what it gets asked to predict.

The next two chapters add the rest of what a chat product does. <Ch slug="reasoning" /> gives the model room to think before it answers. <Ch slug="agents" /> lets it act on the world rather than only talk about it.
