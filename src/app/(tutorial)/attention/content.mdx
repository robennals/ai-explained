# Paying Attention

<Lead>
In the last chapter, we saw that predicting the next token requires understanding, but our models could only look at a fixed window of recent tokens. What if the model could look at all the previous tokens and pick out the ones that hold the information it needs? That idea, called attention, is the breakthrough that makes modern AI work. And it's built entirely from things you already know.
</Lead>

## Some Tokens Need Other Tokens

You often can't tell what a token means without looking at other tokens in the sentence. The token "bank" could be a place for money or the side of a river. You need to see the tokens around it to know which one. A pronoun like "it" makes no sense on its own. You have to look back and find what it refers to.

Each sentence has a highlighted token. Follow the arrow to the other token you need in order to understand it. Flip through the examples. The thing a token needs can be a pronoun's referent, the doer of an action, the scene a token sits in, or a name mentioned long ago.
</WhyAttentionMattersWidget>

The kind of information a token needs is different every time. "it" needs the thing it stands for. "opened" needs whoever did the opening. "sky" needs the planet it hangs over. "treaty" needs a name from far back in the passage. There's no fixed rule for what to look at, or for how far back it sits.

That makes this a general problem, and a hard one: take a token, work out what it's missing, and go find the other tokens that have it. Doing it well is most of what makes a model understand a sentence. That is what **attention** does. It lets a token reach back over every earlier token, decide which ones hold what it needs, and pull that information in.

## Searching for a Match

In attention, we imagine each token asking a question and looking around to see which other tokens might have the answer. You can think of this like a Google search. Each token gets three things:

- Its **query** is what it's looking for, like the keywords you type into a search box.
- Its **key** is what it advertises to other tokens, like the title of a web page.
- Its **value** is what it hands over once it's picked, like the content of the page.

To understand a token, attention matches its query against the keys of all the other tokens, then pulls in the value of whichever one fits best. The match doesn't have to be exact. "it" is looking for the thing being talked about, and "glass" has a key that says exactly that. But "bank" is looking for a river or money, while "river" only has a key for "a river." That isn't a perfect match, but it's close enough that "river" still wins.

## Matching with the Dot Product

How does a computer tell whether a query matches a key? In the chapter on vectors, we saw that the **dot product** of two vectors measures how similar they are. So if we represent each query and each key as a vector, the dot product tells us how well they match. A big dot product means a strong match, and the matched token's value gets pulled in.

<MatchingQuestionsWidget>
The same examples, with the query and key now scored. The score is the dot product of the query and the key. The "bank" example is a loose match and still wins.
</MatchingQuestionsWidget>

From here on we'll write each query and key as the plain-English keywords they stand for, and the match as a single score. Underneath, each is a vector and the score is a dot product. We just won't keep writing out the numbers.

## Dividing Your Attention

A token has a fixed budget of attention, 100%, and needs to *divide* that budget among all the other tokens according to their match scores. We turn the raw scores into percentages that add up to 100%. You'll find out why the attention needs to add up to 100% later.

The function usually used for this is called **softmax**. Think of it as a competition: bigger numbers dominate, smaller numbers get squeezed, and the result is a set of percentages.

<SoftmaxExplorerWidget>
Drag the sliders. Try "All equal": everyone gets 25%. Try "Moderate, rest silent": A wins by default because nobody else is saying anything. Try "Moderate meets loud": B drowns out A. The gaps between scores matter more than the absolute values. Softmax cares about who's loudest *relative to everyone else*.
</SoftmaxExplorerWidget>

Now apply softmax to the match scores from before. When one token is the clear best match, it takes almost all of the attention. When two tokens tie, the attention splits evenly between them.

<AttentionSoftmaxWidget>
Each token gets a share of the asker's attention, and the shares always add up to 100%. Try "A split": "he" could mean Sam or Alex, so the attention divides evenly. Try "A clear winner": "glass" takes almost everything. Then drag the query strength up and watch the leftover attention on the weak matches shrink away.

That query strength slider is a real lever the model controls. A longer query vector is a more sensitive detector, the same idea from the Vectors chapter, so a strong query makes the best match dominate and starves the weak ones. A weak query leaves the attention spread out.

There's a catch, though. Softmax always hands out the full 100%, even when nothing in the sentence is a good match. What should a token do when it's looking for something that just isn't there?

## Where Does Attention Go When Nothing Matches?

Softmax always allocates 100% somewhere, even when no real match is available. We need a sensible place for the leftover attention to go.

The fix is to add a **sink** token whose only job is to absorb leftover attention. Give it a key that's *slightly* nounish, enough to score above nothing but well below a real noun. When a real noun is around, the noun wins by a wide margin, because of the cranked-up query magnitude. When no noun is around, the sink wins by default, since it's the only thing scoring above zero.

That handles the case where "it" can't find a noun. The other case, an off-task token like "blah" that isn't looking for a noun at all, needs one more touch: the sink also advertises a generic "nothing in particular" signal, and off-task tokens point their query at exactly that. So a token with nothing to look for still has somewhere harmless to land, and the sink is the only token that matches it.

<ToyAttentionSinkWidget>
Click "it" in `cat blah blah it`: almost all attention goes to "cat," with barely any leftover on the sink. Try `blah blah blah it`: there's no noun to find, and the sink wins ~97% of the attention. Try clicking "blah": it isn't looking for a noun, so its attention parks on the sink (also ~97%). Every off-task token now has somewhere harmless to land.
</ToyAttentionSinkWidget>

Real models don't always use a dedicated sink token. Sometimes the model learns to use a punctuation mark as a sink, or a start-of-sentence token, or just has the token attend to itself. The idea is the same in every case: when this head doesn't have anything useful to do for a particular token, attention has to go somewhere harmless.

## What Did You Find?

So far attention tells us *where to look*, which tokens are relevant. But we also need *what to gather* from those tokens.

Each token gets a third vector: a **value**. The query and key decide who talks to whom. The value is what gets said. For our pronoun example, the value encodes which animal the token represents: cat's value is `[1, 0]`, dog's value is `[0, 1]`, and filler tokens (including the sink) have nothing to share, so their value is `[0, 0]`.

Attention then blends these values using the softmax weights as a recipe. If "it" pays nearly 100% attention to "cat" and a fraction of a percent everywhere else, the result is roughly `[1, 0]`, almost pure cat.

<ToyAttentionValuesWidget>
Click "it" in `cat blah blah it`: the result is almost all cat. Try `cat blah dog it`: half cat, half dog, because "it" matched both nouns equally and the model can't tell which. Try `dog blah dog it`: *two* dogs, and the result is even sharper than with just one. Try `blah blah blah it`: there's no noun to find, attention falls on the sink, and the result vector is empty. That's exactly what "nothing useful gathered" looks like.
</ToyAttentionValuesWidget>

Two of the same noun produces a *more* confident answer than one, not a doubled one. Softmax-weighted blending stays in the same value-space as the input, no matter how many matches there are. Match dog twice, you get dog. Match dog and cat, you get half-dog-half-cat. The mechanism never produces "double dog."

When attention falls on the sink (whose value is `[0, 0]`), the result is empty. That's a clean way to represent "this head had nothing useful to say."

## Where the Vectors Come From

We've been talking about query, key, and value vectors, but where do they actually come from?

The answer is the same one we've run into many times before. The model uses gradient descent to learn the weights that make it perform best and thus minimize its error.

To be more precise, the model learns a simple one-layer neural network (without an activation function) that transforms the token's current embedding into query, key, and value vectors. Nobody hand-writes "this token advertises nounness." The model discovers, from its training data, what's worth looking for and what each token should offer.

And the model doesn't stop at one set of these weights. It learns several, side by side, which is the last piece of the picture.

## Multi-Headed Attention

Go back to "bank." To work out which kind of bank it is, the token is really looking for two different things at once: a nearby river, and nearby money. A single query looks for one thing, so one round of matching can't cover both.

A token often needs to look for more than one thing like this. The answer is to let it look several times over, each in its own separate round of attention. An **attention head** is one such round: one set of queries, keys, and values, learning one pattern of who attends to whom. A model runs many heads in parallel, and each is free to learn a different thing to look for. This is called **multi-headed attention**. Each head produces its own version of every token, and those versions are combined into one that gets passed on.

It's like having several friends. You don't take every question to one person. You ask the hiking friend about trails, the cooking friend about recipes, the doctor friend about that weird rash. Each friend is a separate place to look for a different kind of thing. Each head works the same way: a separate round where a token looks for one kind of thing and gets one kind of answer. Run enough of them and a single token can chase down everything it needs at once, what it refers to, who acted, which clause it belongs in.

<KeyInsight>
Multiple attention heads let the model look for many different things in parallel. Each head has its own query, key, and value weights, so each learns to attend to a different kind of relationship: pronouns, grammar, structure, semantics. **The model doesn't need to choose one kind of attention; it gets all of them at once.**
</KeyInsight>

In real models, every head also has its own sink behavior, because no single head can apply to every token in every sentence. A pronoun-resolving head will be on-task for pronouns and idle for everything else. That idle behavior is what the sink is for.

## What We've Built

Attention is:

1. **Query, key, value.** Each token looks for something (query), advertises what it has (key), and offers an answer (value), like a search.
2. **Match scores.** Each query and key combine via dot product to score how relevant each token is to each other token.
3. **Softmax.** Turn relevance scores into percentages that add up to 100%.
4. **The sink.** A place for attention to go when nothing relevant is around, so off-task tokens have somewhere harmless to land.
5. **Values blended.** The value vectors get blended together using the softmax weights.
6. **Multiple heads.** Run many attention patterns in parallel, each specializing in a different relationship.

But our attention mechanism has no idea *where* tokens are, only *what* they are. "The dog chased the cat" and "the cat chased the dog" produce identical attention scores. In the next chapter, we'll fix this with a trick involving rotation.
