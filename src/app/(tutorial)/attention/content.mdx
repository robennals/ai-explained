# Paying Attention

<Lead>
In order to understand what a word means, we need to look at other words in the document, including words that might have occurred much earlier. Attention is how we do that.
</Lead>

## Some Tokens Need Other Tokens

You often can't tell what a token means on its own. Take "bank": is it a place for money, or the side of a river? You have to look at the tokens around it. A token like "it" is even harder, because it can refer to pretty much anything and we don't know what it is referring to unless we look back to find what it refers to.

</WhyAttentionMattersWidget>

Different tokens need different things in order for us to understand what they mean. "it" needs the thing it stands for. "opened" needs whoever did the opening. "sky" needs the planet it hangs over. "treaty" needs a name from pages ago.


## Searching for a Match

Each token goes looking for the tokens that can help it, a bit like typing a Google search. To do this it gets three things:

- Its **query** is what it's looking for, like the words you type into a search box.
- Its **key** is what it advertises to the other tokens, like the title of a web page.
- Its **value** is what it hands over once it's picked, like the contents of the page.

To understand a token, attention compares its query against every other token's key and pulls in the value of the best fit. A token writes its own query and key from just itself, so it can only look for what it can guess from its own meaning. "it" is a pronoun, so it looks for a thing it might stand for, and "glass" advertises that it's a physical object. Those aren't the same words, but they line up, so it's a strong match. "bank" wants a river or money; "river" only offers a river. That's half of what "bank" asked for, but it's enough, so "river" wins.

## Matching with the Dot Product

How does a computer decide whether a query matches a key? So far they've been plain English, but inside the model they are **vectors**: lists of numbers that stand for meaning. To score a match, the model takes the **dot product** of the query and the key. The dot product is a simple recipe that turns two lists of numbers into one number showing how much they line up (the [chapter on vectors](/vectors#measuring-similarity) builds it from scratch). When the query and key line up, the number is big and the match is strong. When they point different ways, it's small.

The same examples, with the query and key now scored. The score is the dot product of the query and the key. The "bank" example is a loose match and still wins.
</MatchingQuestionsWidget>

From here on we'll write each query and key in plain English and the match as a single score. Underneath they're still vectors and dot products; we just won't spell out the numbers every time.

## Dividing Your Attention

Usually more than one token matches, at least a little. So instead of crowning a single winner, attention blends the values together, giving each token a say in proportion to how well it matched. First it turns the raw scores into percentages that add up to 100%, one slice of attention per token.

The tool for this is called **softmax**. Think of it as slicing a pie: the highest scores get the biggest slices, low scores get slivers, and the slices always add up to one whole pie.

<SoftmaxExplorerWidget>
Drag the sliders. Try "All equal": everyone gets 25%. Try "Moderate, rest silent": A wins by default because nobody else is saying anything. Try "Moderate meets loud": B drowns out A. The gaps between scores matter more than the absolute values. Softmax cares about who's loudest *relative to everyone else*.
</SoftmaxExplorerWidget>

The gap between the scores is what matters. When one token is the clear best match, it takes almost all of the attention. When two tokens tie, the attention splits evenly between them. We'll see both cases when we gather the values.

## What Did You Find?

Now the token collects its answer. Each token also carries a **value**: the information it hands over when another token picks it. The searching token adds up the values it paid attention to, each one weighted by its slice of attention. A clear winner gives a sharp answer. A tie gives a real blend of both.

<AttentionValuesWidget>
Try "A clear value": "it" pays almost all its attention to "glass", so it gathers "the glass". Try "An even split": "it" could be the cat or the dog, so it gathers "either the cat or the dog". Try "A leaning blend": "pounced" is looking for the agile animal that pounced, which fits the cat better than the dog, so it gathers "probably the cat, maybe the dog".
</AttentionValuesWidget>

Because the slices add up to 100%, the answer always stays in the same range as the values that went in. It can never overshoot into "double cat". And a blend is often the right call: an unclear pronoun really is a mix of options until later words settle it.

## When Nothing Matches

Sometimes a token looks for something that isn't there. The "it" in "It was raining" doesn't stand for anything; English just wants a subject. With no good match, softmax still hands out the full 100%, so the attention smears across every token and the answer is mush.

The fix is a **sink**: an extra token whose value means "nothing" and that faintly matches everything. A real answer easily beats it, but with no real answer the sink wins by default, so the token safely gathers nothing.

<AttentionSinkWidget>
Try "Nothing matches": no real token fits, so the sink takes most of the attention and "It" gathers nothing. Try "Something matches": "glass" scores far above the sink, so it wins and the sink is ignored.
</AttentionSinkWidget>

Real models don't always add a dedicated sink token. Often they just learn to dump spare attention on a comma, the first token, or the token itself.

## Where the Vectors Come From

Where do a token's query, key, and value actually come from? Nobody writes them by hand. Each token starts as a vector that captures its meaning, and the model multiplies that vector by three sets of learned numbers to produce the query, the key, and the value.

Those numbers are set by training. The model makes a guess, checks how wrong it was, and nudges its numbers to do a little better, over and over, millions of times (an [earlier chapter](/optimization) shows how). Nobody tells it "this token advertises being a noun." It works out for itself what's worth looking for and what each token should offer.

And it doesn't stop at one set of numbers. It learns several sets at once, which is the last piece of the picture.

## Multi-Headed Attention

One query looks for one thing. But "bank" needs two at once: a nearby river and nearby money. So attention runs many times over. Each round is a **head**, with its own queries, keys, and values, and each head learns to look for something different. This is **multi-headed attention**, like asking different friends different questions: the one who hikes about trails, the one who cooks about recipes.

Run enough heads and a single token can chase down everything it needs at once: what it refers to, who acted, which words describe it.

## What We've Built

Attention is:

1. **Query, key, value.** Each token looks for something (query), advertises what it has (key), and offers an answer (value), like a search.
2. **Match scores.** The dot product of a query and a key scores how well two tokens fit.
3. **Softmax.** Turn those scores into percentages that add up to 100%.
4. **The sink.** A safe place for attention to go when nothing in the sentence fits.
5. **Blended values.** Combine the chosen values using those percentages.
6. **Many heads.** Run the whole thing many times over, each head looking for something different.

One thing is still missing: attention has no idea *where* the tokens are, only *what* they are. "The dog chased the cat" and "the cat chased the dog" give exactly the same scores. The next chapter fixes that with a trick involving rotation.
